# 生成追踪采用业务存储，评测证据独立导出

- 关联：[需求 REQ-01～06](../phase/2026-11-07-generation-observability-evaluation/PRD.md)、[方案 D1](../phase/2026-11-07-generation-observability-evaluation/PROPOSED_DESIGN.md)。

工作台需要在现有 Redis 任务快照过期后查询七天内的完整步骤，并执行应用所有权、删除和记录完整性规则。评测报告则需要单独保留，不能随着在线追踪过期而失去依据。

因此采用 OpenTelemetry 表达调用关系，在现有 MySQL 新增 `generation_trace` 与 `generation_trace_step` 两表作为工作台追踪的查询事实源；Redis 继续负责原任务执行状态和幂等。评测通过隔离环境中的独立 Java 命令执行，结果导出为维护者管理的本地文件。查询接口和创建请求编号按兼容方式接入，详细字段、接口、迁移与恢复契约以方案第 4 节为唯一来源。

只扩充 Redis 快照会混淆两种生命周期；只使用外部追踪平台会让产品权限、删除和完整性依赖另一套后端；只用本地 JSONL 支撑工作台，则需要额外解决多用户查询、并发和清理。采用 MySQL 的代价是新增表、写入与清理逻辑，但可以沿用现有数据与授权边界。

追踪故障不改写正常生成结果，缺失记录必须明确标注。创建关联未确认时拒绝展示详情；已删除应用立即不可查，迟到绑定按追踪编号清理，无法恢复的关联按七天规则清理。评测报告独立保留，记录完整性、供应商用量完整性和业务评测结果分别判定。

此次批准只完成设计文档，不授权执行迁移、编码或发布。不改旧业务表、不回填虚构历史；后续回退代码不自动删除追踪表，已清理数据不能靠代码回退恢复。实际实现与验证后才更新当前架构事实。
